# 项目文档结构化规范

本规范用于在初始化项目记忆时整理目标仓库已有文档，并为后续文档生成建立轻量规则。目标不是建立项目看板，而是让人和智能体都能从少量入口找到权威文档、理解文档之间的关系，并避免相同主题继续无序堆积。

## 职责边界

- `docs/` 保存可长期引用的项目文档，例如架构、指南、运行手册、参考资料、决策、计划和验证报告。
- `project-memory/` 保存足以接管的项目摘要、当前工作流、最近进展和只追加工作记录，并链接到权威文档。
- 智能体入口文件只保存稳定行为规则和入口指针，不保存文档目录副本、近期进展或部署细节。
- 代码、配置、OpenSpec 或仓库已经采用的其他变更系统继续保持其权威性；不得为了统一外观而把内容复制进 `docs/`。

## 调查现有文档

先识别仓库真实使用的文档目录、README、索引、变更规范和生成文档。若已有结构清晰且持续维护的约定，优先沿用，不强制改成模板目录。

对 Markdown 文档建立内部盘点表，至少判断：

| 字段 | 需要回答的问题 |
| ---- | -------------- |
| 路径 | 文档当前在哪里，是否属于依赖、生成物或外部资料？ |
| 主题 | 它说明哪个领域、模块或操作？ |
| 类型 | 它是架构、指南、运行手册、参考、决策、计划、报告还是历史资料？ |
| 状态 | 当前有效、草稿、已被替代、仅供历史参考，还是无法判断？ |
| 权威性 | 它是当前权威来源、摘要、派生结果，还是与其他文档冲突？ |
| 关系 | 它依赖、补充、验证或替代哪些文档？哪些文档会引用它？ |
| 动作 | 保留原位、加入索引、补关系、待核对，还是满足条件后移动？ |

不需要为盘点而逐行阅读所有文档。先根据路径、文件名、标题、首段和现有链接分类；只有判断权威性、冲突或迁移风险时再深入阅读相关文档。

## 推荐分类

分类用于导航，不是强制目录清单。只生成目标项目实际需要的分类；空分类不创建。

| 分类 | 内容 | 常见目录 |
| ---- | ---- | -------- |
| 架构与设计 | 系统边界、模块关系、数据与执行设计 | `architecture/`、`design/` |
| 开发与使用 | 开发指南、用户指南、示例和迁移说明 | `guides/`、`tutorials/` |
| 运维与部署 | 部署、运行手册、排障、备份与恢复 | `operations/`、`runbooks/` |
| 参考资料 | API、协议、配置和稳定术语 | `reference/` |
| 计划与决策 | 尚未完成的计划、已接受的设计决策 | `plans/`、`decisions/` |
| 验证与报告 | 测试、评估、审计和阶段性结果 | `reports/` |
| 历史与归档 | 已被替代或只为追溯保留的资料 | `archive/` |

一个文档只进入一个主要分类索引，避免在多个列表中复制维护；需要表达跨领域关系时使用“相关文档”链接。若仓库已经有更合适的领域分类，使用现有名称并在文档首页解释其含义。

## 生成关系层

初始化时使用 `assets/项目文档/` 生成或保留式补齐以下关系层：

```text
docs/
├── 首页.md
├── 文档规范.md
└── 索引/
    └── <实际存在的分类>.md
```

- `docs/首页.md` 是文档图谱的根，只保存分类入口、当前权威入口、待核对问题和图谱提示。
- `docs/索引/<分类>.md` 连接具体文档，并区分当前有效、草稿或计划、已替代或历史资料。
- 具体文档可以在确有帮助时加入“相关文档”小节，表达依赖、补充、验证、替代或被替代关系。
- `project-memory/首页.md` 链接 `docs/首页.md`；项目记忆继续负责当前接续，文档首页不复制工作流进度。

所有 Obsidian 双链从仓库根编写。图谱的最小关系应为“文档首页 → 分类索引 → 具体文档”；不要为了让图谱更密而添加没有语义的链接。

## 与工作产物建立关系

文档图谱不仅表示分类，还应连接产生和使用这些文档的工作：

```text
分类索引 ──归类──> 项目文档
工作流   ──当前依赖──> 项目文档
工作记录 ──参考──> 项目文档
工作记录 ──新建/更新/移动/替代──> 项目文档
```

- 工作流只链接当前目标仍需使用的权威文档，避免随历史增长。
- 每篇工作记录在“参考文档”中链接实质影响本次判断、设计或操作的文档，不记录所有打开过的文件。
- 每篇工作记录在“文档产物”中完整链接本次新建、更新、移动或明确替代的项目文档，并标明动作。
- 代码、配置、OpenSpec、报告、Issue 或提交等其他产物继续在工作记录的改动、验证或引用中链接。

这些关系由工作流或工作记录单向指向文档即可。Obsidian 会在文档侧提供反向链接，关系图谱也能展示连线；不要仅为了增加回链而不断修改权威文档。只有来源工作本身构成文档必须理解的背景时，才在文档正文中加入明确的工作记录链接。

当前工作记录自身和工作流的例行收尾更新不重复列为文档产物；只有工作流或 Project Memory 稳定笔记发生独立、实质变化时才列入。每次必读的协议和入口也不自动成为参考文档，避免所有节点无差别连接到同一组文件。

## 处理旧文档

默认保留旧文档路径。初始化可以直接完成以下安全动作：

1. 创建或补齐文档首页、规范和实际需要的分类索引。
2. 把已有文档链接到一个主要分类，并在索引中注明无法确认的状态或冲突。
3. 对明显相关且正在编辑的文档补充少量关系链接。
4. 把依赖目录、构建产物和外部镜像文档排除在项目文档图谱之外，必要时在首页说明排除范围。

只有同时满足以下条件时才移动或重命名旧文档：

- 已确认它是项目自有文档，不是生成物、依赖或外部同步副本；
- 新分类明确，不涉及有争议的权威来源合并；
- 能找到并同步更新仓库内全部入链、脚本路径和导航入口；
- 移动后执行链接或引用检查，且用户规则没有要求保持原路径。

无法满足时保留原位并通过索引建立结构。不得默认删除、合并或改写内容相似的文档；重复、冲突和疑似过期内容先列入“待核对”，说明判断依据。

## 新文档生成规则

创建文档前先判断内容去向：

1. 只是当前目标、进度、阻塞或交接信息，写入 `project-memory/`。
2. 属于仓库已有变更协议的提案或任务规范，写入该系统并从相关索引链接，不复制正文。
3. 属于可长期引用的项目说明，放入最接近的现有文档分类。
4. 没有合适分类时，先判断是否真的需要新分类；单篇文档不为自己创建一层目录。

每次新增、移动或明确替代一篇权威文档时：

- 更新对应分类索引；
- 必要时更新 `docs/首页.md` 的权威入口或待核对项；
- 在强相关文档之间补充有语义的链接；
- 已替代文档保留历史入口并指向替代它的文档，不把历史内容继续描述为当前事实。

不强制给全部旧文档批量添加 frontmatter。若目标仓库已经使用元数据，沿用现有字段；若没有，只在新建或实质更新的文档中按需使用 `type`、`status` 和 `updated_at`，索引仍是主要导航来源。

## Obsidian 图谱

仓库根目录继续作为 Vault。文档首页、分类索引、关系链接和具体文档都跟随当前 Git checkout；切换分支或提交后，图谱自然反映该版本的仓库内容，不维护跨分支的外部图谱状态。查看项目文档时，在全局关系图谱中使用：

```text
path:"docs/"
```

需要同时观察文档与项目接续关系时使用：

```text
path:"docs/" OR path:"project-memory/"
```

建议开启箭头并关闭孤立文件；颜色组优先按项目已有文档目录或分类索引划分。图谱用于发现关系和进入内容，不替代索引中的状态说明，也不证明文档仍然有效。

## 验收

完成结构化处理后应满足：

1. 用户和智能体都能从 `docs/首页.md` 在两跳内找到每篇纳入管理的项目文档。
2. 每篇文档只有一个主要分类；跨分类关系通过链接表达。
3. 当前权威文档、草稿计划、历史资料和无法判断项不会混成一个无状态列表。
4. 重复、冲突、孤立和疑似过期文档可见，但未被擅自删除或合并。
5. 新增的双链和移动产生的全部引用都能解析。
6. 文档图谱与 Project Memory 分工清楚，近期进展不会再次堆入权威文档导航。
7. 工作记录能够区分本次实质参考的文档和本次产生或修改的文档；从文档反向链接能够找到相关工作历史。
